# DB 복원 절차 (#1291 · #1292 빈 DB 틀 만들기 · 2026-11-25)

> 배포 때마다 만드는 백업(`scripts/db-backup.js` → OneDrive `제주아꼼이네_DB백업/backup_<버전>_<날짜>.sql`)으로 DB 를 되살리는 순서.
> 🔴 복원은 그 DB 의 **모든 표를 비우고** 백업 시점으로 덮는다. 대표 결정 없이 실DB 에 돌리지 않는다.
> 비밀값(접속 주소·비밀번호)은 이 문서·대화·커밋에 적지 않는다 — 환경 변수로만 넘긴다.

## 0. 먼저 알 것

- 백업 파일 = **자료만**(TRUNCATE → 표마다 INSERT → 시퀀스 복구). **표 틀(CREATE TABLE)은 없다.**
- 표 틀 = 저장소 `scripts/db-schema.sql`(#1292 · `scripts/db-schema-dump.js` 가 실DB 틀만 읽어 찍음 · 자료 0 · 표 107·시퀀스 87·인덱스·외래 키 36·생성 칸까지). 빈 새 DB 는 `--init` 으로 이 파일부터 실행한다(2절). 서버 initDB 만으로는 빈 DB 에 틀이 다 안 만들어진다.
- 복원 = `node scripts/db-restore.js <파일> --yes` · 한 트랜잭션(하나라도 실패하면 전부 되돌림 · DB 는 시도 전 그대로).
  - 큰 파일(512MB 넘음)도 흘려 읽음(#1288) · 외래 키는 잠시 내렸다가 끝에 다시 걸며 전 줄 검사(#1288).
  - 부분 백업(`BACKUP_TABLES`)·「표 백업 실패」 줄이 든 파일은 거절한다(#1291) → 그 앞 백업 파일로. 실패 줄은 따옴표 밖 줄 머리 주석만 본다(#1292 · 손님 글 안에 같은 글자가 있어도 거절하지 않음).
  - 시작 때 「🎯 대상 DB: 호스트:포트/DB이름」이 찍힌다 — **이 줄이 맞는 DB 인지 반드시 눈으로 확인.**
- 🔴 **파일 꼴 두 가지**
  - **새 꼴(#1291 배포 뒤 만든 파일)**: 그대로 복원된다(로컬 실자료 규모 시험 = 107표 214,932줄 · 다시 백업하면 바이트 같음).
  - **옛 꼴(#1291 이전 · 11/24 v5.9.853 까지)**: 그대로는 **안 된다** — ①jsonb 안 숫자·문자열 값이 날것(`agent_office_config` 15줄 안팎) ②생성 칸(`delivery_shipments.phone_digits`·`buyer_digits`)이 INSERT 에 들어 있음 ③배열(`order_memo_entries.tags`)이 JSON 꼴. 옛 꼴을 써야 하면 총괄에게 — 시험 때 쓴 「사본 손보기」 길(#1288 보고)로 사본을 만들어 넣는다. ①의 문자열 `"5"` 같은 값은 옛 꼴에서 이미 숫자와 구분이 사라져 숫자로 돌아온다.
  - 512MB 이하 옛 파일(11/19 v5.9.830 이전 일부)은 예전 복원 스크립트로도 읽혔지만 ①~③ 과 외래 키 순서 탓에 역시 실패한다.

## 1. 자료만 잘못된 경우 (DB·표 틀은 살아 있음)

1. 대표 결정 받기 — 어느 백업 시점으로 되돌릴지(그 뒤 들어온 주문·기록은 사라진다).
2. 🔴 **회사프로그램 서버를 멈춘다(세운다)** — Render 에서 서비스 Suspend. 돌고 있으면 타이머·러너가 복원 중인 표에 쓰기를 섞는다.
3. 지금 상태도 한 번 더 백업(`node scripts/db-backup.js 복원전`) — 되돌릴 길.
4. 복원: `node scripts/db-restore.js backup_<버전>_<날짜>.sql --yes`
   - 「🎯 대상 DB」 줄 확인 → 「✅ 복원 완료」까지(실자료 규모 로컬 38초 · Render 256MB DB 는 더 걸릴 수 있음).
5. 대조: 표마다 `count(*)` = 백업 파일의 `-- <표> (N건)` 줄 숫자.
6. 서버 다시 켜기 → 로그인·발주 메모함·최종발주 화면 스모크.

## 2. DB 가 통째로 사라진 경우 (새 DB 에 틀부터 · `--init`)

1. Render 에서 새 PostgreSQL 생성(같은 큰 판 18) → 접속 주소는 **환경 변수로만**(.env·코드에 넣지 않음). 회사프로그램 서버는 멈춘 채로.
2. **틀 파일 고르기** — 되살릴 백업과 **같은 버전의** `scripts/db-schema.sql` 을 쓴다. 틀이 백업보다 옛것이면 없는 칸에서 멈추고(롤백), 새것이면 남는 칸은 기본값으로 채워진다.
   - 틀 파일이 든 태그(**v5.9.856 부터** · #1292 커밋 뒤 첫 배포 태그)의 백업 = 그 태그의 틀: `git show v5.9.<버전>:scripts/db-schema.sql > 틀.sql` → `--init=틀.sql`.
   - 그 이전 백업(855 까지 · 태그에 틀 파일 없음) = 지금 `main` 의 틀(`--init` 만). 예: 854·855 백업 → main 틀 · 854 에 없던 `naver_auto_collect.fail_count` 칸은 기본값으로 채워진다(로컬 시험에서 확인). 멈추면 2절 5 를 본다.
3. **틀 + 자료 한 번에**: `DATABASE_URL=<새 DB> node scripts/db-restore.js backup_<버전>_<날짜>.sql --init --yes`
   - PowerShell 꼴: `$env:DATABASE_URL='<새 DB 주소>'; node scripts/db-restore.js backup_<버전>_<날짜>.sql --init --yes` (끝나면 `Remove-Item Env:DATABASE_URL` · 주소는 화면·기록에 남기지 않기)
   - 다른 틀 파일 = `--init=틀.sql` · 「🎯 대상 DB」 줄이 **새 DB** 인지 눈으로 확인.
   - 한 트랜잭션 = BEGIN → 빈 DB 확인 → 틀(표 107·시퀀스·인덱스·외래 키) → 외래 키 잠시 내림 → 자료 → 외래 키 다시 걸며 전 줄 검사 → COMMIT. 어디서 실패해도 새 DB 는 텅 빈 채 그대로.
   - 🔴 대상 public 에 표·시퀀스·뷰가 **하나라도 있으면 거절**(「--init 거절: 대상 DB 가 비어 있지 않음」) — 틀이 있는 DB 면 1절(`--init` 없이)로. 새 DB 의 public 에 확장이 만든 뷰·표(pg_stat_statements 등)가 있어도 「비어 있지 않음」으로 거절된다(안전 쪽) → 그 확장을 지우거나 확장 없는 새 DB 로.
   - 로컬 실측(PG 18.1 · 854 백업 922MB) = 아래 「시험 기록」.
4. 대조: 표마다 `count(*)` = 백업 파일의 `-- <표> (N건)` 줄 숫자.
5. (멈췄을 때) 「칸 … 없음」 = 틀 파일이 백업보다 옛것 → 그 버전 태그의 틀로 다시. 「표 … 없음」 오류에 「--init 을 붙이세요」가 같이 뜨면 `--init` 을 빠뜨린 것.
6. 서버 환경 변수 `DATABASE_URL` 을 새 DB 로 → 서버 켜기(initDB 는 이미 있는 표·칸이라 그냥 지나감) → 스모크 · 타이머 첫 틱 확인.

## 3. 틀 파일 새로 찍기

- `node scripts/db-schema-dump.js` → `scripts/db-schema.sql` 을 새로 씀 · `--check` = 파일과 지금 DB 틀이 같은지만(다르면 종료 1).
- 읽기만(READ ONLY · 시스템 목록만 · 자료 줄 0 · 시퀀스 지금 값도 안 읽음) · 같은 DB 면 늘 같은 바이트(이름순 · 날짜 줄 없음) → `git diff` 에 틀 변화만 보인다.
- 🔴 저장소가 PUBLIC — 파일에는 표·칸 이름·타입·기본값 식만 들어간다. 기본값 따옴표 글자에 비밀값·메일·연락처·주소(://) 꼴이 있으면 도구가 쓰지 않고 멈춘다. 뷰·함수·트리거·확장·identity·상속 같이 이 도구가 못 담는 것이 DB 에 생겨도 멈춘다(조용히 빠뜨리지 않음 → 도구를 먼저 넓힐 것).
- 틀을 바꾸는 배포(initDB 에 표·칸 추가) 뒤에 다시 찍어 커밋한다. (제안 · 총괄 확인 전) `npm run deploy` 의 백업 단계 뒤에 `db-schema-dump.js --check` 를 붙여 다르면 알려 주기.
- 서버 initDB 와 실DB 틀이 다른 까닭(그래서 틀 파일이 필요함): initDB 가 빈 DB 에서 순서 탓에 멈춤(`users`·`message_logs` 참조 · 14표·70표에서) · 처음 쓸 때 만드는 표 20개가 initDB 밖(desk-inbox.js·inbox-threads.js·response-head.js·naver-mail.js·push.js·scripts/desk/invoice-month.js·lucky-event.js·톡톡봇 저장소 server.js 등) · 검증이 남긴 시험 표(lucky_events_ro* 등)·옛 표(unmatched_messages)도 실DB 에 있어 틀 파일에 들어간다.

## 4. 하지 말 것

- 서버가 돌고 있는 채로 복원.
- 부분 백업·「백업 실패」 줄이 든 파일로 복원(스크립트가 거절함 — 우회하지 말 것).
- 실DB(자료 있는 DB)에 `--init` — 거절되지만 시도하지 말 것.
- 실백업 파일을 저장소·공유폴더에 복사(손님 정보) — 시험은 로컬 임시 DB 에서, 끝나면 DB 와 사본을 지운다.
- 틀 파일을 손으로 고치기(다음 찍기에서 덮임 · 고칠 것은 DB 쪽에서).

## 5. 남은 일(후보)

- initDB 순서 정리(빈 DB 에서 1번에 다 만들어지게) — `--init` 이 생겨 급하지 않음.
- 배포 때 틀 파일 낡음 알림(3절 제안).

## 시험 기록

- #1292 (2026-11-25 · 로컬 PG 18.1 · 실DB 18.3 = 틀 읽기만): 빈 DB → `--init` → 854 백업(922MB) = 39초 · 표 107 · 218,936줄(백업 머리 숫자와 표마다 같음) · 외래 키 36 · 시퀀스 87 · 인덱스 189.
  - 틀 대조 = db-schema-dump 로 다시 찍으면 바이트 같음 · 따로 `pg_dump --schema-only` 로도 실DB = 로컬(2,537줄 같음).
  - 다시 백업 = 854 원본과 내용 같음(표마다 줄 묶음 대조 · 단 시간대를 원본 DB 와 같은 UTC 로 둘 때) · 다른 것 = 855 배포로 생긴 `naver_auto_collect.fail_count` 칸(틀이 더 새것 = 기본값으로 채워짐) · 몇 표는 줄 순서만 다름(내용 같음 · 까닭 모름).
  - 빈 DB 아닌 곳(표 있음·시퀀스 하나만 있음) `--init` = 거절·종료 1·자료 그대로 · `--init` 없이 빈 DB = 실패·롤백 + 「--init 을 붙이세요」 · 틀 있는 DB 에 `--init` 없이 = 종전처럼 덮어 복원.
  - 복원한 DB 위에서 서버 initDB(바깥 연결 막음) = 오류 0 · 틀 안 바뀜.
- 🔵 시간대: 백업은 timestamptz 를 「그 DB 세션 시간대」 글자로 적는다(Render = UTC). 새 DB 의 시간대가 달라도 같은 순간으로 들어가 값은 같다 — 다시 백업한 파일 글자만 달라 보인다.
