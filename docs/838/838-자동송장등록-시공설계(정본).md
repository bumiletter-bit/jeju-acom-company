# #838 자동 송장 등록 — 시공 설계 정본 (대표 결정 2026-10-24 · 총괄 claude-9f 정리)

> 새 워커(Opus 가능)가 이 문서 + 같은 폴더의 838A·838B·838C 보고만 보고 시공할 수 있게 적음.
> 대표 「고」 가 떨어지면 시작. 그 전엔 무접촉. 🔴 무회귀 = 최종발주(final-order.js·final-order-core.js·invoice-v2.js)의 기존 판정·파일 산출은 한 글자도 바꾸지 않는다. 새 기능은 **최종발주 화면의 새 단추 + 새 서버 라우트 + 새 표** 로만 붙인다.

## 1. 대표가 그린 흐름(확정)

1. 최종발주 끝 → 거래처별 택배사 양식 2개를 거래처가 CJ 프로그램(LOIS)에 올림(지금과 같음 · 무변경).
2. CJ 에서 나온 **운송장 시트(시트2 꼴 · 거래처별 2개 · 시트1 없이 그 파일만)** 를 에이전트 오피스 › 최종발주 화면 **[자동 송장 등록]** 에 올림.
3. 프로그램이 운송장 1줄 1줄을 그날 주문과 짝 맞춤 → **확인 카드**(최종발주 카드 꼴) → 대표/직원이 [등록] → 3채널 API 발송처리 → 결과 표(성공 n · 실패 n · 실패 줄은 수기용 파일).
4. 카드 전엔 외부로 아무것도 안 나감. 같은 주문 두 번 등록 금지(멱등 열쇠 = 채널+주문번호+운송장).

## 2. 짝 맞추기 규칙(대표 확정 · 838B 실측 10/23 = 자동 246/248)

| 경우 | 규칙 |
|---|---|
| 기본 | 운송장 줄의 **받는분 이름 + 받는분 전화(숫자) + 주소(공백 제거)** 가 그날 주문과 **셋 다** 같을 때만 자동. 하나라도 다르면 자동 금지(오매칭 > 미매칭 · 메모리 jeju-invoice-matching-policy). |
| 수량 2 주문 = 운송장 2줄 | 둘 다 그 주문 것. 채널엔 **첫 운송장 1개**(채널 한계 = 주문 1건 송장 1개). 나머지는 송장 색인(delivery_shipments)에 남아 문자 봇·배송조회가 답함. 자동. |
| 같은 분이 품목 다른 두 주문 | 시트2 「상품명」 칸으로 가름 → 자동. |
| 같은 분이 **같은 품목** 두 주문 | **아무거나 1개씩** 배정(대표 결정 · 카드 아님). |
| 입력삭제(주문 통째 개별 주소 · 현금파일 줄로 나감) | 그 주문의 스토어 주소(주문자/수취인 주소)와 같은 운송장이 있으면 **그것** · 없으면 **그 주문자 번호로 나간 운송장 중 아무거나 1개**(대표 결정 · 카드 아님). 짝 열쇠 = 구매자 번호(시트2 「보내는분 전화」에 보존됨 · 838B) + 현금 줄 주소. |
| 현금 「!」 줄(보내는이에 「!」) | **등록 대상 아님**(거래처 주문건 아님) · 카드에 「송장만」 표시. |
| 지정발송일(「번호 27일발송」) | 그날 최종발주에 **포함 안 됨**(지금 로직 그대로 excluded) → 운송장도 없음 → 아무 일 없음. 27일이 되면 보통 메모를 안 쓰므로 일반 주문으로 들어옴. 메모에 날짜를 다시 쓰는 경우 = 손님이 배송메세지에 30일이라 썼다가 27일로 바꿔 연락 → 혼동 막으려 「27일」 로 적는 것 = 그날 포함(parseDate 가 오늘 = 포함). |
| 사이즈(「번호 s사이즈」) | 등록 무관(옵션 꼬리 「S사이즈로!」 는 시트2 상품명에 보존 · 짝 열쇠에 안 씀). |
| 보내는이 변경 | 등록 무관(양식만). 🔵 「드림」 낱말은 지금 인식 안 됨(SENDER_KEY 에 없음 · 838C ④) — 별도 1줄 후보. |
| 짝이 안 맞는 줄 | **카드 할 일**(운송장 번호·받는분 가림 표시 · 사람이 주문을 고르거나 「수기」로 둠 → 실패 파일). |
| 선물하기(구매자 번호 가림 「가*가」) | 주 열쇠(받는분 이름+번호+주소)로 됨(838B). |

## 3. 채널 구분·주문 재료

- 시트2 만으론 채널·주문번호를 모름(838B). → [자동 송장 등록] 누를 때 **3채널 「불러오기」 API 를 그대로 재조회**(naverFetchInvoiceOrders v2 · coupangFetchInvoiceOrders · cafe24 invoice-orders · 모두 읽기 · 종전 코드 재사용)해서 상품주문번호/shipmentBoxId/order_item_code + 수취인·연락처·주소·수량을 얻어 운송장과 짝. 최종발주 결과를 따로 보관할 필요 없음(🔵 선택 = 최종발주 「정리」 때 주문별 행을 90일 보관하면 입력삭제·지정발송일 표시를 그대로 쓸 수 있음 — 2차).
- 날짜요청 건은 운송장이 없어 저절로 빠짐.

## 4. 3채널 전송(대표 결정 「발송처리 자동 허용」 = 「고」 때 확정)

| 채널 | 호출 | 지금 막힌 것 | 푸는 일(총괄) |
|---|---|---|---|
| 네이버 | POST /external/v1/pay-order/seller/product-orders/dispatch (productOrderId · deliveryMethod DELIVERY · deliveryCompanyCode CJGLS · trackingNumber) | relay 바디 검사가 #782 NOTHING(체험)만 통과 | relay/server.js 검사 확장(CJGLS+12자리 숫자 허용) → install.sh(SSH 열쇠 · 메모리 jeju-relay-ssh-key) · RELAY_VERSION 올림 |
| 쿠팡 | POST /v2/providers/openapi/apis/api/v4/vendors/{vendorId}/orders/invoices (shipmentBoxId · deliveryCompanyCode CJGLS · invoiceNumber · splitShipping false) | relay COUPANG_ALLOW 에 없음 | 허용 1줄(vendorId 강제 · 숫자 자리) · 공식 문서 r.jina.ai 재대조 |
| 자사몰 | POST /api/v2/admin/shipments (order_id · tracking_no · shipping_company_code(CJ) · order_item_code[]) | scope 에 mall.write_shipping 없음 | 카페24 개발자센터 권한 추가 → **대표 재승인 클릭 1번**(🔴 #479 함정 = 권한 등록 전에 재승인 요청하면 실패) · 공식 문서 재대조 |

- 발송처리는 **취소 API 가 없다**(틀린 송장 = 알림톡·배송조회·구매확정 틀림) → 카드 확인 전 전송 0 · 첫 1~2주는 카드에서 몇 건을 채널 화면과 눈으로 대조.
- 전송 뒤 = lms_guide_log/주문안내 흐름은 종전(네이버 발송처리 뒤 trackingNumber 를 알림톡이 읽음)이라 무접촉.

## 5. 화면·서버 설계(새 것만)

- **화면**: 최종발주 화면(public/final-order.js) 맨 아래 새 묶음 「자동 송장 등록」 = 파일 2개 끌어다 놓기(xlsx · 거래처 자동 판별 = 보내는분 이름·파일명) → [짝 맞추기] → 카드(채널별 n · 자동 n · 할 일 n(짝 안 맞음·입력삭제 선택) · 현금 n(송장만) · 수량2 n) → [등록] → 결과 표 + [실패 줄 내려받기]. 폴드7 한 줄 · 44px · 인디고 가이드.
- **서버**: `POST /api/agent-office/invoice-auto/match`(파일 → 3채널 재조회 → 짝 결과 JSON · 외부 쓰기 0) · `POST /api/agent-office/invoice-auto/register`(짝 결과 id + 선택값 → 3채널 전송 · 멱등 · 결과 저장) · 새 표 `invoice_auto_runs`(날짜·파일 해시·짝 결과·선택·전송 결과 · 90일 · 전화번호 가림) · audit source invoice-auto.
- **송장 색인 겸함**: 올린 시트2 는 지금 ship-upload(server.js 11178 LOIS 파서)와 같은 꼴 → 같은 자리에서 delivery_shipments 색인도 같이(대표 PC 색인 올리기가 필요 없어짐 · 종전 길은 남김).
- **권한**: 전 직원 올리기·카드 보기 · [등록] 은 대표·조가영(관리자) — 종전 「외부 설정은 누구나」 원칙과 다르면 대표 확인.
- **검증**: scripts/verify-838-invoice-auto.js(가짜 pool · 가짜 3채널 응답 · 838C 하네스 t838c.js 의 가짜 주문 8 + 10/23 꼴 시트2 가짜 50줄 · 규칙표 2절 전부 · 멱등 · 전송 0) + 실자료 1회(대표 「고」 뒤 첫 실행은 카드까지만 · [등록] 전 대표 눈).

## 6. 바퀴·순서(가늠 2.5~3일 + 카페24 승인)

1. 서버 짝 맞추기 + 카드 JSON + 검증(워커A · 1일) — 외부 쓰기 0 이라 먼저 배포해 **카드까지만** 실자료로 돌려 봄.
2. 화면(워커B · 0.5일) · 읽기 점검(워커C).
3. relay 2곳 + 카페24 scope(총괄 · 대표 클릭) → 전송 라우트 + 검증(워커A · 1일) → 교차 점검 → 배포 → 첫 실발송은 대표 입회 1건부터.
4. 업무지식 「자동 송장 등록」 절 + 메모리 플레이북.

## 7. 「고」 때 대표가 줄 것

- 입력삭제·현금 「!」 줄이 있는 날의 시트2 파일 1쌍(규칙 실측용).
- 쿠팡·자사몰 주문이 섞인 날 시트2 1개.
- 카페24 재승인 클릭(총괄이 권한 추가한 뒤 알림).
