## 1. 네이버 — 발송 처리

- 원문: apicenter 「발송 처리」(seller-dispatch-product-orders-pay-order-seller · 2.90.1).
  - 「단수 또는 복수 개 상품 주문을 발송 처리합니다. 요청 가능한 상품 주문 번호는 최대 30개입니다.」
- 바디(칸은 이 다섯 개뿐):
```json
{ "dispatchProductOrders": [
  { "productOrderId": "2026102438638821", "deliveryMethod": "DELIVERY", "deliveryCompanyCode": "CJGLS",
    "trackingNumber": "123456789012", "dispatchDate": "2026-10-24T17:30:00.000+09:00" } ] }
```
- `deliveryMethod` 코드표: DELIVERY(택배·등기·소포) · NOTHING(배송 없음) · DIRECT_DELIVERY · QUICK_SVC · VISIT_RECEIPT 등 11개. 우리는 **DELIVERY만** 쓴다(체험은 종전대로 NOTHING).
- `deliveryCompanyCode`: 코드표의 첫 줄이 「CJGLS = CJ대한통운」이다(「KOREXG = CJ대한통운(국제택배)」와 헷갈리지 말 것).
- `dispatchDate`: date-time 이고 예시는 `2022-04-05T12:17:35.000+09:00` 이다. relay 는 밀리초와 +09:00 이 있는 꼴만 받는다(#782 종전).
- 응답(200) — 실패가 섞여 있어도 200 으로 온다:
```json
{ "timestamp": "…", "traceId": "…", "data": {
  "successProductOrderIds": ["…"],
  "failProductOrderInfos": [{ "productOrderId": "…", "code": "…", "message": "…" }] } }
```
- 400·500 응답 = `{ code, message, timestamp, traceId }`. 400 예시에는 위 data 꼴도 함께 실려 있다.
  - → **HTTP 상태만 보지 말고 data 의 두 목록으로 줄마다 판정한다.** 두 목록 어디에도 없는 줄은 「모름」으로 둔다(재시도 금지 · 수기 확인).
- 실패 code 값 목록은 문서에 없다. message 원문을 그대로 저장한다.

## 2. 쿠팡 — 송장업로드 처리

- 원문: developers.coupang.com 「송장업로드 처리」(uploading-waybills · URL API NAME UPDATE_ORDER_SHIPPING_INFO).
- 「상품준비중 상태의 주문에 대해서만 송장업로드가 가능합니다.」 → 우리 발주확인(#402 · ACCEPT→INSTRUCT)을 거친 주문만 된다. 불러오기가 읽는 INSTRUCT 가 바로 그 상태다.
- 「6개월 이내에 중복된 송장번호를 입력할 경우 송장중복에러」. 단 「수취인의 이름과 주소가 동일한 서로 다른 주문은 동일한 송장번호 가능」.
- 바디(8칸 모두 필수 `*`):
```json
{ "vendorId": "A00012345",
  "orderSheetInvoiceApplyDtos": [
    { "shipmentBoxId": 644466823, "orderId": 4000022521677, "vendorItemId": 3937239983,
      "deliveryCompanyCode": "CJGLS", "invoiceNumber": "123456789012",
      "splitShipping": false, "preSplitShipped": false, "estimatedShippingDate": "" } ] }
```
- **한 상자에 옵션이 여럿이면 옵션마다 한 줄씩, 같은 invoiceNumber 로 보낸다.**
  - 공식 예시도 같은 shipmentBoxId 의 두 vendorItemId 를 같은 송장으로 두 줄 보낸다.
  - 한 줄이 빠지면 `NOT_FOUND_VENDOR_ITEM`(「합포장건 중 누락된 상품」)이 난다.
- 분리배송(splitShipping true)은 쓰지 않는다. relay 도 막는다.
  - 상품이 하나뿐인 주문은 분리배송 자체가 안 된다(`NOT_ALLOW_SEPARATE_WHEN_ONE_VENDOR_ITEM`).
  - 박스 2개(수량 2)는 송장 1개(첫 운송장) = 정본 2절 그대로다.
- 택배사 코드표(logistics/courier-code): `CJGLS | CJ대한통운 | 10 또는 12 | 1234567890, 680405450931`.
- 응답:
```json
{ "code": "200", "message": "OK", "data": { "responseCode": 0, "responseMessage": "SUCCESS",
  "responseList": [{ "shipmentBoxId": 644466823, "succeed": true, "resultCode": "OK", "retryRequired": false, "resultMessage": null }] } }
```
- `responseCode` 값: -1 NONE · 0 SUCCESS · 1 PARTIAL_ERROR · 99 FAILED.
- `resultCode` 값(괄호는 retryRequired):

| resultCode | 다시 해도 되나 |
|---|---|
| OK | false |
| NOT_FOUND_SHIPMENT_BOX | false |
| INVALID_STATUS | false |
| PERMISSION_DENIED | true |
| DUPLICATE_INVOICE_NUMBER | true |
| INVALID_INVOICE_NUMBER | true |
| ORDER_DELIVERY_CANCELED | false |
| ORDER_DELIVERY_PARTIAL_STOP_REQUESTED | true |
| ORDER_DELIVERY_CANCELED_HOLDING_FOR_CANCEL | true |
| UNDEFINED_ERROR_OCCUR | true |
| NOT_ALLOW_INVOICE_NUMBER_RE_UPLOAD | false |
| NOT_FOUND_INVOICE_NUMBER | false |
| NOT_FOUND_VENDOR_ITEM | false |
| NOT_ALLOW_VENDOR_DIRECT | false |
| PSD_NOT_ALLOW_TO_CHANGE | false |
| NOT_ALLOW_SEPARATE_AFTER_NORMAL_DELIVERY | false |
| IS_SEPARATE_MUST_BE_TRUE_WHEN_SEPARATE_DELIVERY | false |
| NOT_ALLOW_SEPARATE_WHEN_ONE_VENDOR_ITEM | false |

  - 🔴 「다시 해도 된다」(true)고 와도 자동 재시도는 하지 않는다. 취소대기·출고중지 요청 건이 섞여 있다 → 카드 「실패 줄」로 사람에게 보낸다.
- 400 오류 예(문서): 「CJ 대한통운의 송장번호 형식에 맞지않는 운송장 번호」 · 「CJ 대한통운의 운송장번호는 숫자로만 구성되어야 합니다」 · 「invalid delivery company code」.
- 🔵 번호 정밀도: 문서 예시의 shipmentBoxId `123456789012345680` 은 2^53 을 넘는다(예시가 깨진 값으로 보임).
  - 실제 우리 값은 9~12자리라 안전하다.
  - relay 바디 검사는 숫자면 안전 정수만, 글자면 숫자 1~20자리를 받는다 → **회사프로그램은 불러오기 행의 글자 값(_shipmentBoxId·_orderId·_vendorItemId)을 Number() 하지 말고 그대로 보낸다.** 쿠팡이 글자 숫자를 받는지는 실측 1건으로 확인한다. 안 받으면 Number(값)과 안전 정수 검사를 붙인다.
- 호출 상한: 쿠팡 rate-limit 공지(종전 docs/728)를 따른다. 한 번에 50줄씩 0.5초 간격(우리 규칙).

## 3. 자사몰(카페24) — 배송 정보 등록

- 원문: apidocs.cafe24.com(2026-09-01판).
  - 「여러건 배송 정보 등록」 POST `/api/v2/admin/shipments` — scope **WRITE_ORDER** · 호출제한 40회/초 · 요청제한 100건.
  - 「주문 배송 정보 등록」 POST `/api/v2/admin/orders/{order_id}/shipments` — 같은 scope · 1건.
  - 🔴 설계 정본·838A 에 적힌 「mall.write_shipping」은 틀렸다. shipping scope 는 배송사(carriers) 관리용이다.
- 여러 건 바디:
```json
{ "shop_no": 1, "requests": [
  { "order_id": "20261024-0000017", "order_item_code": ["20261024-0000017-01"], "tracking_no": "123456789012",
    "shipping_company_code": "<우리 몰 CJ 코드>", "status": "shipping" } ] }
```
  - 필수 칸 = tracking_no(≤40자) · shipping_company_code · status(`standby` 배송대기 / `shipping` 배송중).
  - 선택 칸 = order_id · shipping_code · order_item_code[] · carrier_id.
- 주문별 경로 바디: `{ "shop_no":1, "request": { tracking_no, shipping_company_code, order_item_code[], status, shipping_code?, carrier_id? } }`.
- 응답 예(성공):
```json
{ "shipments": [{ "shop_no": 1, "shipping_code": "D-20190320-0000024-00", "order_id": "…", "status": "shipping",
  "tracking_no": "…", "shipping_company_code": "0001", "order_item_code": ["…-01", "…-02"], "carrier_id": 1 }] }
```
  - 오류 코드 = 400 · 401 · 403(권한 = scope 없음) · 404 · 422 · 429 · 500.
  - 상태 코드 가이드: POST 성공 = 201 · 여러 건 부분 실패 = **207**(객체별 status·message) → 207 이면 줄마다 판정한다.
- **status = `shipping`** 으로 보낸다(우리 몰은 결제 즉시 N20 배송준비중 → 배송중).
  - `standby` 는 쓰지 않는다.
  - tracking_no 가 생기면 자사몰 발송안내(E 알림톡 · server.js 11564)가 저절로 나간다.
- **3-3. CJ 코드값 = 아직 모름(추측 금지)**
  - 문서 예시의 `"shipping_company_code": "0001"` 은 `"shipping_company_name": "DHL"` 과 짝이다(주문 품목 조회 예시).
  - 코드표 링크(shipping_company_code)는 실렌더에서 열리지 않았다.
  - 확정하는 길(재승인 뒤 · 읽기만): `GET /api/v2/admin/carriers`(scope read_shipping)로 우리 몰 배송사 목록을 받아 「CJ대한통운」 줄의 `shipping_carrier_code` 와 `carrier_id` 를 읽는다.
  - 또는 지난 자사몰 주문 중 송장이 들어간 주문 1건을 `GET orders/{id}/items` 로 읽어 shipping_company_code·name 을 확인한다(read_order · 지금도 가능).
  - → 값을 설정 `invoice_auto.cafe24_carrier_code` 에 넣는다(코드에 박지 않음).

- **멱등 열쇠**: 지금처럼 `채널:주문키`(네이버 productOrderId · 쿠팡 shipmentBoxId · 카페24 order_id)로 둔다. 쿠팡·카페24 는 **상자·주문 단위로 묶어** 한 송장만 보낸다.
  - 지금 card row 의 order_key 는 쿠팡 `상자|옵션` · 카페24 `주문|품주`라서 전송 전에 묶어야 한다(교차 점검 C).
- **보내기 전에 줄을 집는다**: `UPDATE invoice_auto_items SET state='sending' WHERE idem_key=$1 AND state IN ('ready') RETURNING …` → 보낸 뒤 `sent` 또는 `failed`(code·message).
  - 응답을 모르면 `unknown` 으로 둔다. 다시 보내지 말고 사람이 채널 화면을 보고 정한다. 발송처리는 취소 API 가 없다.
- **already 판정은 `sent`·`sending`·`unknown` 일 때만** 한다. dry 로 준비만 한 줄(ready)은 새 실행이 덮어쓴다(교차 점검 A).
- 순서: 네이버 → 쿠팡 → 카페24. 채널마다 실패해도 다음 채널로 간다. 줄 사이 간격 = 네이버 350ms(종전) · 쿠팡 0.5초 · 카페24 묶음 1번.
- 끝나면 audit `invoice_auto_send`(채널별 ok·fail·unknown 수) · 텔레그램은 실패가 있을 때만 1회.
- 카드에 더할 칸(전송에 필요 · 교차 점검 B): 네이버 `product_order_id` · 쿠팡 `order_id`·`vendor_item_id` · 카페24 `order_id`·`item_code`(이미 있음).
