# STEP E — 네이버 상품문의(Q&A) 자동답변 설계서 (v2 — 자동 게시)

> 작성: 2026-07-26 밤 (v1 승인 게시) → **2026-07-27 v2: 대표 지시로 자동 게시 구조로 변경**
> 대상: 스마트스토어 판매자센터 **상품문의(Q&A, 공개 게시판)**
> 구조: 수집 → AI 배정 → **확신 건 자동 게시 / SKIP·애매 건만 직원 답변 대기** (톡톡봇과 동일한 완전 자동 구조)
> 잘못된 게시는 매일 확인하며 **판매자센터 화면에서 수정** (대표 운영 방침).

---

## 0. 핵심 사실 확인 (설계 전 검증 결과)

1. **상품문의(Q&A)는 현재 수집되지 않고 있다.** 가동 중인 30분 문의 수집기(`collectInquiry`)는
   `GET /external/v1/pay-user/inquiries` = **고객문의(문의하기)** 전용. 상품문의(Q&A)는 별도 API(`contents/qnas`)이며
   중계서버 ALLOW에 **읽기 경로조차 없다** (ALLOW는 pay-settle·pay-order/seller·pay-user·seller만 GET 허용).
   → **읽기 1줄 + 쓰기 1줄, 총 2줄** ALLOW 추가 필요.
2. DB의 `naver_inquiries`는 현재 **2건뿐** (수집기가 7/26 가동 시작, 조회 창 3일 — 과거분 없음).
   실문의 분석 재료는 **`message_logs`(톡톡봇 실메시지 947건, 6/11~7/25, 직원 실답변 570건)** 를 사용했다. §8 참조.
3. 봇 조회 API(`GET /api/scenarios`) 채널 필터: `talktalk → ['톡톡','공통']`, `product → ['상품문의','공통']`.
   → 기존 톡톡 시나리오를 '공통'으로 전환해도 톡톡봇 동작 무영향(계속 내려감). 상품문의 전용은 채널 '상품문의'로 신규 등록.
4. 서버에 Anthropic SDK + `ANTHROPIC_API_KEY`(Render) + `MARU_MODEL`(기본 claude-haiku-4-5) 이미 사용 중 — AI 배정에 재사용.
5. **답변 수정 가능 여부 (v2에서 재확정)**: 공식 문서 제목 원문 **"상품 문의 답변 등록/수정"**, 설명 원문
   **"상품 문의의 답변을 등록하거나 수정할 수 있습니다."** — 같은 PUT으로 **API 수정 가능**. API에 DELETE(삭제)는 없음.
   판매자센터 화면에도 답변 수정란 존재(대표 확인). → 잘못된 자동 게시는 판매자센터에서 수정하는 운영이 성립.

## 1. 답변 등록 API 스펙 (공식 문서 확정 — 추측 없음)

문서 출처: `apicenter.commerce.naver.com/docs/commerce-api/current/` (r.jina.ai 프록시로 열람)
- 목록 조회: `get-comments-contents` 페이지
- 답변 등록/수정: `create-or-update-answer-contents` 페이지

### 1-1. 상품문의 목록 조회 (읽기)
- `GET https://api.commerce.naver.com/external/v1/contents/qnas`
- 쿼리: `fromDate`·`toDate`(date-time, **필수**), `page`(기본 1), `size`(기본 100, **최대 100**), `answered`(boolean, 선택)
- 응답 `contents[]`: `questionId`(integer, 고유키), `productId`, `productName`, `question`(문의 내용),
  **`answer`(판매자 답변 — 직원 실답변 수집 가능)**, `answered`(boolean), `createDate`, `maskedWriterId`(마스킹된 작성자 ID)
- 페이징: `page`/`size`/`totalElements`/`totalPages`
- ⚠️ 조회 기간 상한은 문서에 명시 없음 → 시공 시 고객문의와 동일하게 **최근 3일 창**으로 보수 운용(30분 주기라 충분한 겹침).

### 1-2. 상품문의 답변 등록/수정 (쓰기 — 이번 프로젝트의 유일한 쓰기)
- `PUT https://api.commerce.naver.com/external/v1/contents/qnas/{questionId}`
- 경로 파라미터: `questionId` (integer, 필수)
- 요청 바디: `{ "commentContent": "답변 내용" }` (필수. 글자수 제한은 문서 미명시 — 시공 시 2,000자 자체 상한)
- 성공: **204 No Content**. 오류: 400/401/403/404/500 (`code`·`message`·`invalidInputs[]`·`traceId`)
- 등록과 수정이 같은 PUT — **우리 시스템은 미답변 건에만 호출**(등록 용도로만 사용).
  수정·정정은 판매자센터 화면에서 수동(자동 재호출로 기존 답변을 덮어쓰는 사고 방지).

## 2. 아키텍처 (톡톡봇 방식 — 완전 자동 + 직원 폴백)

```
[30분 타이머 qna 수집기]                        [문의 관리 › 상품문의 탭]
collectQna
  ├ GET contents/qnas (최근 3일)                  ├ 🤖 자동 게시됨 목록 (매일 확인용
  ├ naver_qnas upsert (질문 마스킹)                │    — 문구·시나리오명 표시,
  ├ 신규 미답변 → AI 배정(배정만)                   │    수정은 판매자센터에서)
  │   ├ 확신 채택 → PII 검사 →                     ├ ✍️ 직원 답변 필요 목록 (SKIP·애매·
  │   │   [자동 게시 스위치 ON?] → PUT 게시          │    PII 걸림·게시 실패) — 직원 작성
  │   │   (OFF면 초안으로 대기 = 승인 모드)          │    → [게시] 버튼 → 동일 쓰기 함수
  │   └ SKIP/애매/PII 걸림 → 직원 답변 필요          └ 자동 게시 ON/OFF 토글 (대표 전용,
  └ 텔레그램: 자동 게시 M건·직원 필요 K건               기본 ON)
```

- **자동 게시 스위치**: `agent_office_config` 키 `qna_auto_post`, **기본 'on'** (대표 지시).
  OFF → 승인 모드로 즉시 전환: 자동 게시만 멈추고, 확신 건은 초안 상태로 "직원 답변 필요" 목록에 쌓여
  [게시] 버튼으로 수동 게시(v1 승인 흐름 그대로). 토글은 대표 전용(기존 `inquiry_auto_reply` 스위치와 동일 정책).
- **쓰기 함수는 공용 1개** `naverPostQnaAnswer(questionId, content, actor)`:
  PII 검사(§3)를 **함수 내부에 강제 내장**(어떤 호출자도 우회 불가) + audit 기록 + 미답변 건 검증.
  호출 지점은 정확히 2곳 — ①수집기 자동 게시(actor='auto') ②[게시] 버튼 라우트(actor=계정). 그 외 없음.
- 기존 문의 수집기(`collectInquiry`)·톡톡봇·시나리오 로직은 **무수정** (추가만).
- **내장 단계적 가동**: 채널 '상품문의'/'공통' 시나리오가 0건인 동안은 배정이 전부 SKIP → 자동 게시가 일어나지 않음.
  대표가 시나리오를 등록·전환하는 유형부터 하나씩 자동화가 켜지는 구조(별도 코드 불필요).

### 2-1. AI 배정 (배정만 — AI 문장 생성 금지, 톡톡봇 규칙 동일)
- 대상 시나리오: `inquiry_scenarios`에서 `channel IN ('상품문의','공통') AND enabled AND deleted_at IS NULL`.
- **1차: 키워드 매칭** (톡톡봇과 동일한 결정적 로직, 공백 제거 포함 매칭).
  - 정확히 1개 시나리오만 매칭 → 그 시나리오 채택(확신).
- **2차: LLM 판정** (1차가 0건 또는 2건 이상일 때만): Claude(`MARU_MODEL`)에게 질문 원문 + 시나리오 목록(번호·이름·키워드)을
  주고 **"시나리오 번호 하나 또는 SKIP"만** 출력받는다(JSON 강제, temperature 0). 형식 위반·불확실 → SKIP.
- 채택 시 **게시 문구 = 해당 시나리오의 `response` 그대로** (변형·생성 금지). `{{가격표}}`/`{{판매현황}}` 플레이스홀더는
  서버가 `bot_products`로 치환(봇과 동일 규칙)한 결과를 게시.
- SKIP → `ai_status='skip'` ("직원 답변 필요"). 침묵 정책 유지.
- 배정·자동 게시는 **수집 시점에 신규 미답변 건당 1회만** — 반복 호출·중복 게시 방지(게시 성공 기록 필수 선행).

### 2-2. DB
```sql
CREATE TABLE IF NOT EXISTS naver_qnas (
    question_id  BIGINT PRIMARY KEY,
    raw          JSONB,            -- product_name·question(마스킹)·create_date·masked_writer_id 등 최소 필드
    answered     BOOLEAN,          -- 네이버 기준 답변 여부 (수집 시 갱신)
    ai_status    VARCHAR(10),      -- 'posted'(자동 게시) | 'draft'(승인 대기) | 'skip' | NULL(미배정)
    ai_scenario_id INTEGER,        -- 채택 시나리오 id (참고용)
    ai_draft     TEXT,             -- 게시(예정) 문구 (플레이스홀더 치환 후)
    posted_at    TIMESTAMP,        -- 게시 성공 시각 (자동·수동 공통)
    posted_by    VARCHAR(50),      -- 'auto' 또는 게시자 계정명
    post_error   TEXT,             -- 마지막 게시 실패 사유 (성공 시 NULL)
    collected_at TIMESTAMP DEFAULT NOW()
);
```
- 질문 본문도 고객문의와 동일하게 `naverMaskContact` 마스킹 후 저장.
- 90일 경과분 물리 정리(고객문의와 동일 정책 — 원본은 네이버에 있음).
- `naver_auto_collect`에 `('qna', false, 30)` 시드 — **수집 자체는 기본 OFF**(중계서버 ALLOW 반영 전 켜면 403 실패 표시됨).
  `agent_office_config`에 `qna_auto_post='on'` 시드(자동 게시 스위치 — 수집이 켜져야 의미 있음).

### 2-3. 게시 경로 2곳 (공용 쓰기 함수 경유)
- **자동**: `collectQna` 내부 — 신규 미답변 + 배정 확신 + `qna_auto_post='on'` 일 때만.
  실패 시 `post_error` 기록 + "직원 답변 필요"로 강등 + 텔레그램 1회.
- **수동**: `POST /api/agent-office/naver/qnas/:id/answer` — `authMiddleware`(**직원 포함**), 바디 `{content}`.
  SKIP 건 직원 작성·승인 모드 초안 게시 겸용. 이미 `posted_at` 있거나 네이버 `answered=true`면 거부.
- 두 경로 모두: PII 통과 → PUT 204 → `posted_at`·`posted_by` 기록 →
  `writeAudit(action:'post_answer', targetType:'naver_qna', source:'naver-qna', actor)` (자동 게시도 actor 'auto'로 기록).

### 2-4. 알림 (기존 알림 설정 화면에 'qna' 키 추가)
- `TELEGRAM_ALERT_KEYS`에 `'qna'` 추가, 기본 문구:
  `🛒 상품문의 신규 {{건수}}건 — 🤖 자동 게시 {{게시}}건 · ✍️ 직원 답변 필요 {{직접}}건`
- 게시 실패 시 별도 고정 문구 1회. 기존 고객문의(inquiry) 알림은 무수정.

### 2-5. 화면 ([문의 관리] 4번째 탭 "🛰️ 상품문의")
- 상단: 자동 게시 ON/OFF 토글(대표 전용) + 상태 요약(오늘 자동 게시 n건·대기 n건).
- 목록 구분: **✍️ 직원 답변 필요**(SKIP·애매·PII 걸림·실패 — 위로) / **🤖 자동 게시됨**(매일 확인용 — 게시 문구·시나리오명·시각 표시,
  "수정은 판매자센터에서" 안내) / ⚠️ 실패(사유 표시).
- 직원 답변 필요 건: 질문 전문 + 입력창(위에 "이름·주문정보 언급 금지" 고정 안내) + [게시] 버튼.
- 디자인은 `디자인/디자인_가이드.md` 준수.

## 3. 개인정보(PII) 게시 차단 검사 — 공용 쓰기 함수 내부, 모든 게시 직전 필수 통과

공개 게시판이므로 아래 패턴 검출 시 **게시 차단 + 사유 표시** (자동 건은 "직원 답변 필요"로 강등, 수동 건은 수정 후 재시도):
1. 휴대폰/전화번호: `01[016789][-\s.]?\d{3,4}[-\s.]?\d{4}`, `\d{2,4}[-\s.]\d{3,4}[-\s.]\d{4}`
   — 단, **고객센터 대표번호(010-6687-4031)는 화이트리스트** (시나리오 문구 공통 꼬리에 포함되어 있음).
2. 이메일 패턴 — 단, 회사 공개 메일(bumiletter@naver.com)은 화이트리스트.
3. 주문번호 의심: 14자리 이상 연속 숫자(`\d{14,}` — 네이버 주문번호 16자리 커버).
4. 주소 의심: `(시|군|구)\s?.{0,12}(로|길)\s?\d` 또는 `\d+동\s?\d+호` 패턴.
5. 고객 이름은 패턴 검출 불가 → 자동 게시 문구는 확정 시나리오뿐이라 구조적으로 안전.
   직원 직접 작성분은 입력창 위 고정 안내로 보완.

## 4. 중계서버 변경 (시공 시 리포 수정 → 대표 SSH 재실행)

`relay/server.js` ALLOW에 **딱 2줄** 추가 + `RELAY_VERSION = '2026-07-27.1'`:
```js
{ m: 'GET', re: /^\/external\/v1\/contents\/qnas$/ },        // 상품문의 목록 조회 (읽기)
{ m: 'PUT', re: /^\/external\/v1\/contents\/qnas\/\d+$/ },   // 상품문의 답변 등록/수정 (이번 프로젝트 유일한 쓰기)
```
- 쓰기는 questionId 숫자 경로 정확 일치만 허용 — 그 외 쓰기 경로 전면 차단 유지.
- 반영 절차(순서 중요): **①시공 커밋·배포(main push) 후** ②대표 SSH → install.sh 재실행(코드가 GitHub main에서 내려받아짐)
  ③`/health`의 RELAY_VERSION으로 반영 확인.

## 5. 시나리오 채널 운용 설계

- 기존 51건(0~50번)은 전부 채널 '톡톡'. **원본 무수정 원칙** 하에:
  - **공통 전환**: 채널 값만 '톡톡'→'공통' 변경(문구 무수정). 봇 무영향(§0-3). 후보 ~25건 — **대표 승인 후** 화면에서 변경.
  - **상품문의 전용 신규**: 공개 게시판 톤(개인정보·개별 주문 언급 없음, 사진 필요 건은 톡톡/전화 유도)으로 신규 등록. 후보 초안 8건.
- ⚠️ 자동 게시 구조에서는 **시나리오 등록 = 해당 유형 자동화 ON**과 같다. 채널 전환·신규 등록을 한 유형씩 늘려가는 것이
  곧 단계적 가동 방법(§2 내장 단계적 가동).
- 채널 변경·신규 등록 모두 기존 [문의 관리] 화면으로 수행(코드 추가 불필요) — 채널 드롭다운 이미 존재.

## 6. 검증 계획 (자동 게시 구조 반영)

1. 시공 후: `node --check server.js`·`node --check public/app.js`, 로컬 문법·라우트 스모크.
2. 배포 → 대표 SSH로 install.sh 재실행 → `/health` RELAY_VERSION `2026-07-27.1` 확인.
