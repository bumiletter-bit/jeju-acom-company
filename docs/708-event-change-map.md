## 0. 요점 (먼저 알아야 할 것)

1. 🔴 **손님이 지금 보는 이벤트 페이지 = 옛 사이트(bum-toolbox)이고, 회사 프로그램 쪽 페이지는 비어 있다.**
   - `event.akkome.com` = CNAME → `bum-toolbox.onrender.com`(nslookup 실측). 회사 서버(jeju-acom-company)가 아니다.
   - 옛 사이트 `/api/lucky/event` = 주문 6,455건 · 고객 2,919명 · `published:true`(추석 이벤트 당첨 발표 중).
   - 회사 서버 `/api/lucky/event` = 주문 0 · `published:false`. **실DB `lucky_events` 0행**(설정을 한 번도 저장하지 않았고, 옛 사이트 백업도 복원하지 않았음 — #471 「대표 지시 대기」가 그대로 남아 있음).
   - 회사 쪽은 행이 없으면 **코드에 박힌 기본값**(lucky-event.js 19~31행: 9/10~9/21 · 경품 3종 · 청귤 제외)을 보여 준다.
   - `lucky.html` 파일은 세 곳이 바이트 같음(로컬 · 회사 라이브 · 옛 사이트 라이브 md5 821891e3…).
   - /guide 카드 url과 시나리오 #59 링크는 둘 다 **`https://event.akkome.com/lucky.html`(옛 사이트)** 로 되어 있다(지금은 둘 다 꺼져 있음).
   - 따라서 **「관리 화면(회사 /lucky-admin.html)에서 고쳐도 손님 주소(event.akkome.com)에는 안 나온다.”** 정본을 정하는 일이 먼저다(아래 2절).
2. 고객 화면에서 이벤트마다 바뀌어야 하는 것 중 **관리 화면으로 바뀌는 것은 제목(화면 읽기용 숨은 글)·기간·발표일·경품 이름·인원·제외 품목뿐**. 그림 9장, 손글씨 7곳, 경품 설명 3줄, 안내 문구 대부분은 **파일에 박혀 있어 코드 수정·배포가 필요하다**.
3. 큰 제목은 그림 속 글자다(`lucky_hero_full.webp` 안의 「고객 감사 이벤트」). 그래서 제목 칸을 바꿔도 손님이 보는 제목은 안 바뀐다.
4. /guide 이벤트 카드는 **화면이 없고 스크립트(apply-449-event.js)로만** 바꿀 수 있다. 시나리오 #59는 **문의 관리 화면에서 직원이 고칠 수 있다**(대신 날짜·링크가 본문 안에 그대로 적혀 있다).
5. 그림을 저장할 곳은 **DB(bytea) + 공개 라우트 + 긴 캐시**를 추천한다(4절). Render 디스크는 배포 때 사라지고, 서버에는 그림 줄이는 라이브러리(sharp 등)가 없으니 줄이기·webp 바꾸기는 브라우저에서 해야 한다.

## 2. 이벤트 페이지가 어디서 서비스되나 (확정)

| | 옛 사이트 | 회사 프로그램 |
|---|---|---|
| 주소 | `https://event.akkome.com/lucky.html` | `https://jeju-acom-company.onrender.com/lucky.html` |
| 서버 | Render **bum-toolbox**(CNAME 실측) · 루트 `/`는 「한라산 코딩」 무료 프로그램 사이트 | Render jeju-acom-company · express.static(public) · 공개 API는 lucky-event.js |
| 저장 | 파일 `data/lucky.json` — **배포할 때마다 사라짐**(#471 이식 사유) | DB `lucky_events`(JSONB 1행=1회차 · 배포해도 남음) |
| 관리 | 관리자 코드(x-admin-code) | 회사 로그인(JWT · 직원 가능) |
| 지금 데이터 | 추석 이벤트 6,455건 · 발표 중 | **0행**(기본값만 보임) |
| 소스 | bum-toolbox 저장소 lucky.js(origin/main 6709f84) — **이 PC에 로컬 사본 없음** | 이 저장소 |

- **정본(설계상) = 회사 프로그램.** #471 에서 옮긴 이유가 「배포마다 소실」이고, 그 뒤 할 일이 ①옛 백업 → 회사 [백업 파일로 복원] ②조회 확인 ③/guide 카드 url과 #59 링크를 회사 주소로 바꾸기였다. 이 세 단계가 **아직 안 됐다**.
- **지금 손님에게 보이는 것(실제) = 옛 사이트.** 회사 쪽에서 무엇을 고쳐도 event.akkome.com 에는 반영되지 않는다.
- 직원 셀프 운영을 하려면 손님 주소를 회사 쪽으로 옮겨야 한다. 후보:
  - (a) DNS: event.akkome.com CNAME 을 jeju-acom-company 로 바꾸고 Render 에 사용자 도메인 추가 — 단 bum-toolbox 의 「한라산 코딩」 루트(/)도 그 주소를 쓰고 있으면 깨짐(확인 필요 · 대표 판단). 회사 서버 `/`는 회사 프로그램 로그인 화면이 됨 → 회사 서버에서 event 호스트로 오면 `/` 를 /lucky.html 로 돌리는 한 줄 필요.
  - (b) 링크만 회사 주소로: 다음 이벤트부터 /guide 카드·#59·홍보물에 `https://jeju-acom-company.onrender.com/lucky.html`(또는 회사 사용자 도메인) 사용. 옛 주소는 추석 결과 조회용으로 남김.
  - 어느 쪽이든 **옛 사이트 추석 데이터(6,455건)를 회사로 복원할지**는 대표 판단(#481 「회사 쪽 복원 여부」 미결). 옛 사이트는 bum-toolbox 를 다시 배포하면 데이터가 사라진다.

### 그림 저장 후보 (🔴 public/img 에 쓰는 길은 안 됨 — Render 디스크는 배포 때 사라짐)

| 후보 | 장점 | 단점 | 크기 |
|---|---|---|---|
| **① DB bytea 표(예: lucky_assets) + 공개 GET 라우트 + `Cache-Control: public, max-age=…, immutable`(주소에 id·해시)** — **추천** | 배포해도 남음 · 이미 같은 꼴 있음(payslips·company_rules PDF bytea · report_files) · 회사 로그인·audit 그대로 · 외부 계정 0 · 회차와 묶어 보관 쉬움 | 서버가 그림을 내보냄(트래픽 조금) · 지난 회차 그림 정리 규칙 필요(db_retention #579) | 지금 그림 9장 합계 약 190KB · webp 로 줄이면 회차당 0.2~0.5MB → DB 193MB/1GB(실측 · 10/15)에 영향 거의 없음 |
| ② 카페24 FTP(`/sde_design/…` 또는 웹FTP) | 카페24 CDN · 회사 서버 트래픽 0 | 업로드 가드가 skin6 경로 한정(#230) · FTP 비번이 서버 env 에 있어야 함 · 허용 확장자 제약(메모리 jeju-cafe24-skin6-ops) · 다른 서비스 장애가 이벤트에 번짐 | 넉넉 |
| ③ 외부 저장소(S3·R2·Cloudinary 등) | CDN · 큰 파일 | **새 계정·키·요금** · 키를 Render env 에 · 지금 구조에 없음 | 넉넉 |
| ④ 힉스필드 결과 주소를 그대로 걸기 | 작업 0 | 주소 유효 기간·외부 의존 · 원본 PNG 가 커서(수 MB) 느림 | — |

- 서버에 그림 줄이는 라이브러리 없음(package.json — sharp·multer 없음) → **브라우저 canvas 로 줄여 webp 로 바꾼 뒤 base64/바이트로 올리는 꼴**(전역 JSON 한도 15MB · 정산 이미지와 같은 길).

## 3. 이벤트 설정 API·표·권한 · 관리 화면 로그인

- 표: **`lucky_events`**(id · title · data JSONB · is_current · created_at · updated_at · archived_at) — 첫 요청 때 CREATE IF NOT EXISTS · 현재 회차 = is_current TRUE 최신 1행 · data = {event:{title,start,end,announce,prizes[],published,drawnAt,excludeProducts[]}, orders[], winners[], excluded[], uploads[], updatedAt}.
- 공개(손님): `GET /api/lucky/event`(15초 캐시) · `GET /api/lucky/winners` · `POST /api/lucky/lookup`(40회/분 · XFF 첫 값 기준 — 참고: #693 에서 다른 공개 POST 는 cf-connecting-ip 로 바꿨지만 이 모듈은 아직 XFF 첫 값 `ipOf`).
- 관리: `/api/agent-office/lucky/state|rounds`(GET) · `orders|remove|event|draw|publish`(POST · **직원 가능**) · `restore|reset|new-round`(POST · **관리자만**). 쓰기는 withLock 직렬화 · audit_logs(source lucky_admin · 개인정보 없이 건수).
- `/event` 가 받는 칸 = title·start·end·announce(각 80자) · excludeProducts · prizes(name 60자·count) · excluded 뿐. **그림·문구·카드 칸 없음.** 알 수 없는 칸은 버림(새 칸을 넣으려면 서버 수정 필요).
- 로그인: lucky-admin 은 같은 출처 localStorage `jwt_token` 을 Bearer 로 씀 → **회사 프로그램에 로그인한 브라우저에서 새 탭으로 열어야** 함(없으면 「회사 프로그램 로그인하러 가기」). 메뉴 = index.html 170행 「이벤트 관리」(새 탭).
- 🔵 「새 회차」는 관리자만 → 직원이 이벤트를 **처음부터** 여는 일은 혼자 못 함(6절).
